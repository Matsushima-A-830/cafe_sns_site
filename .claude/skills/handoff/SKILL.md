# /handoff — 次セッションへの引き継ぎテキスト生成

## このスキルの目的

**コンテキストを持たない次のセッションが、同じ落とし穴を踏まずに実装を始められるテキストを作る。**

引き継ぎの価値は「何を作るか」ではなく **「何を踏むか」** にある。何を作るかはワイヤーとドキュメントに書いてあるので次セッションが自分で読める。書いてないのは、**マイグレーション原文にしか無い罠・既存コードが既に解決済みの問題・テーブルが存在しないという事実**の3つ。ここに字数を割く。

## 起動時に必ずやること

引数で次スコープの画面ID・機能名が渡されていればそれを対象にする。渡されていなければ、まず候補を洗い出してユーザーに決めてもらう（後述「スコープが未確定のとき」）。

**絶対的な原則: 記憶で書かない。** 会話の中で一度読んだ内容でも、引き継ぎテキストに載せる事実は**その場でファイルを読み直して裏を取る**。行番号・ポリシー名・関数シグネチャを間違えた引き継ぎは、次セッションを誤った前提で走らせるぶん、無いより悪い。

## 調査手順

### 1. 現在地を固める

```bash
git log --oneline -5                      # main の最新コミットとPR番号
find app -name "page.tsx" | sort          # 実装済みルート
ls supabase/migrations | sed 's/^[0-9]*_//'   # 実装済みテーブル
```

### 2. 次スコープのワイヤーを読む

`docs/design/wireframes/*.md` の該当 `S_*` セクション。**ワイヤーの各要素を「出せる / 出せない」に仕分ける**のが後段の材料になる。

### 3. 対象テーブルのマイグレーションを原文で読む

**`tables.md` だけで済ませない。** あれは要点のみで、罠は SQL ファイルのコメントにしか書かれていないことが多い。読むのは:
- `create policy` の全文（SELECT が `using (true)` か、本人限定か、`status` で絞るか）
- `create function` の本体と `comment on function`（**戻り値の NULL 可能性・引数の意図・タイムゾーン基準**はここにしか無い）
- `create trigger` と CHECK 制約
- `grant` / `revoke`（anon から呼べるか）
- 列コメント（`comment on column`）

### 4. そのテーブルがアプリから使われているか調べる

```bash
grep -rl "'<table_name>'" app components lib
```

**未使用のテーブルは「RLS とテストは揃っているが誰も読んだことがない」状態**で、実際に読んだ瞬間に初めて問題が出る。引き継ぎ先にその旨を伝える。

### 5. ドキュメントと実装のズレを拾う

`docs/architecture/routing.md` のレンダリング指定（ISR / SSR）が実装可能かを確認する。閲覧者のセッションが要るページは ISR にできない（`pending-items` D23 に既に3件の前例がある）。**ズレていたら「着手時にまずドキュメントを直す」を引き継ぎ項目に入れる。**

### 6. 未作成テーブルを洗い出す

ワイヤーの要素と `supabase/migrations` を突き合わせ、**存在しないテーブルを名指しで列挙する**。次セッションが実装しかけてから気付くのが一番のロスになる。

### 7. 再利用できる既存資産を特定する

同種の画面が既にあるなら、その取得関数・コンポーネント・テストファイルを名指しする。**「自前で書き直すと踏む」ことを明記する** — 既存関数が黙って解決している問題（論理削除の除外・セッション付きクライアントの強制など）は、新しく書いたクエリでは再現されない。

## 落とし穴の探し方（チェックリスト）

調査中、以下に当たったら引き継ぎテキストの「最重要の落とし穴」候補にする。

### 認可・RLS

- [ ] SELECT ポリシーが `using (true)` → **RLS は何も守らない。列も行もアプリ層で絞る必要がある**
- [ ] SELECT が本人限定 → 直に読むと**エラーではなく0件**で返る。集計は `security definer` 関数経由か
- [ ] 非公開列（`guardian_email` `birth_date` `metadata` `external_ids` 等）が同じテーブルにあるか → `select('*')` 禁止を明記
- [ ] INSERT ポリシーが「自分」しか見ていないか → 相手側（ブロック・`status`）のガード漏れ
- [ ] RLS 違反が「0件の成功」で返る経路 → `.insert().select()` で返り行の確認が要る
- [ ] ポリシーが `auth.uid()` を使う → anon では常に真/偽になる条件がないか

### 型・データ

- [ ] `RETURNS TABLE` の Postgres 関数 → **`supabase gen types` は列を non-nullable に生成するが実際は NULL になりうる**
- [ ] `time` 型・曜日・日付の列 → **タイムゾーン基準（JST / UTC）が列コメントに書かれていないか。Vercel のサーバーは UTC**
- [ ] `citext` 列 → 大小無視で一致する。表示には DB 側の綴りを使う
- [ ] 外部から書き換えられる URL 列（`avatar_url` `main_image_path`）→ `isStoragePublicUrl` を通す必要

### 既存コードが解決済みのもの

- [ ] 一覧取得に論理削除・`status` の絞り込みがアプリ層で明示されているか
- [ ] 閲覧者のセッションで読むことが前提になっているか
- [ ] ページング（keyset カーソル）の精度上の注意

### キャッシュ・レンダリング

- [ ] `routing.md` の ISR 指定が実装可能か
- [ ] `generateMetadata` と本体で 404 条件がズレないか（**ズレると404ページのタイトルに非公開情報が載る**）

## 出力フォーマット

以下の構成で**ターミナルに Markdown テキストとして出力する**。ユーザーはこれをコピーして次セッションに貼る。ファイルには保存しない（`docs/` を汚さない）。保存を頼まれたときだけ書き出す。

```markdown
# 引き継ぎ: <スコープ名>（<画面ID>）

## 背景

直近マージした内容 / main の現在のコミット / 「どこまで通ったか」を2〜4文。
今回のスコープを1文で。

着手理由を番号付きで2〜3個。**事実ベースで書く**
（例: 「`post-card.tsx:61` が全カードから404へリンクしている」）。

## 最重要の落とし穴（先に読むこと）

### 1. <見出しは結論を書く>

該当する SQL / コードを短く引用し、何が起きるかを具体的に書く。
ファイルパスと行番号、ポリシー名・関数名を必ず添える。
3〜7個。**重要度順に並べ、最後に「特にこの2つ」と補足で再掲する**。

## 実装済みで使えるもの

| 資産 | 場所 | 用途 |
| ---- | ---- | ---- |

再利用できる関数・コンポーネント・テストを表で。
「自前で書き直すと踏む」ものには理由を添える。

## 新規実装が必要なもの

番号付きリスト。ファイルパス（仮）と、その中で守るべきことを1〜3行ずつ。

## 着手前に決めるべきこと（要判断）

ユーザーの判断が要る分岐を番号付きで。**推奨案と、その判断が何を左右するかまで書く**。

## 関連ドキュメント

パスと、そこに何が書いてあるか。行番号が有用なら添える。

## デザインシステムの注意

そのスコープ特有のもの（表組み・色だけに依存しない表現など）+ 共通の必須ルール。

## Git 運用

ブランチ名の案 / コミット規約 / PR テンプレートの注意。

## 環境メモ

WSL 経由の実行方法・ツールの癖・ローカルDBの状態。**前回から変わった点を反映する**。

## 未確認事項（引き継ぎ）

「実装したがまだ人間の目で見ていない」もの。正直に書く。

## 未解決フォローアップ（今回スコープ外）

pending-items の ID を列挙。

---

**補足:** 一番重要な落とし穴を1〜2個に絞って再掲し、「なぜそれが怖いか」を1文で。
```

## 書き方の指針

- **落とし穴は「結論 → 根拠 → 影響」の順。** 見出しだけ読んで危険が伝わるようにする
- **行番号とポリシー名を書く。** 「RLS に注意」では次セッションは何も確認できない
- **出せないものを理由付きで列挙する。** 「テーブルが無いから出せない」は実装判断そのもの
- **要判断はユーザーに投げる前提で書く。** 次セッションが勝手に決めてよい話と、決めてはいけない話を分ける
- **「これは既に解決済み」を明示する。** 引き継ぎの半分は「やらなくていいこと」の伝達
- **Biome も tsc もテストも素通りする類の罠**は必ず最後の補足で再掲する

## やらないこと

- **コードの貼り付け** — 実装案を書き下さない。次セッションが読むべきファイルを指すだけにする
- **ワイヤーの書き写し** — `docs/design/wireframes/` を参照させる。ただし「出せる/出せない」の仕分けは引き継ぎ側の仕事
- **一般論** — 「テストを書きましょう」は CLAUDE.md に書いてある。このスコープ固有の話だけ書く
- **憶測の混入** — 確認していないことは「未確認」と明記する。断定しない

## スコープが未確定のとき

引数なしで呼ばれた場合、引き継ぎテキストの前に**次に何を実装するかの提案**を行う。
1. 実装済みルート・テーブルと、ワイヤー（37画面）・`mvp-scope.md` を突き合わせて穴を出す
2. 候補を3〜4個に絞り、それぞれ「404リンクを塞ぐか」「幹A/幹Cを進めるか」「マイグレーションが要るか」「依存する未作成テーブル」で比較する
3. **推奨を1つ明示し、`AskUserQuestion` で選んでもらう**
4. 決まってから調査手順に入る

## サイクルの中での位置

**このスキルは1周の終端。** 1周＝1画面＝1PR で、次はセッションを切り替える。

```
① /handoff（引数なし）で候補出し → ユーザーが選ぶ
② 調査 → routing.md 等のズレを先に直す → 要判断を AskUserQuestion
③ 実装: /db-implement →(/test)→ /be-implement → /fe-implement
④ /self-review（規約）→ /code-review（バグ）
⑤ /board-update → db:reset 検証 → PR → CI green → マージ
⑥ /handoff <次の画面ID> → セッションを切る    ← ここ
```

### 走らせる前に満たしておくこと

- [ ] **PR がマージ済み**（`gh pr list --state merged --limit 1` で確認）。レビュー中の内容を
  引き継ぐと、指摘で変わった部分が古い前提のまま次に伝わる
- [ ] **`/board-update` を実行済み**。ボードは引き継ぎテキストとは別物で、どちらも必要
- [ ] 実装中に判明した未決事項が `pending-items.md` に記録済み

### セッションを切る理由

コンテキストが膨らんだ状態のまま次の機能に入るより、引き継ぎテキストを挟んで切ったほうが
精度が出る。**引き継ぎテキストは「圧縮したコンテキスト」ではなく「次が踏む罠のリスト」**なので、
会話の流れを引き継がなくても成立する。

## 他スキルとの関係

- **実装前の設計:** `/fe-implement` `/be-implement` `/db-implement`
- **実装中に詰まったら:** `/debug`
- **実装後のレビュー:** `/self-review`（規約）→ 組み込み `/code-review`（バグ）。両方走らせる
- **実装状況ボードの更新:** `/board-update`（マージ前。引き継ぎテキストとは別に必ず実行する）

## 終了条件

- 引き継ぎテキストに書いた**事実がすべてファイルで裏取り済み**
- 「最重要の落とし穴」が3個以上あり、それぞれにファイルパスか識別子が付いている
- 未作成テーブル・未実装ルートが名指しで列挙されている
- 要判断の項目が挙がっている（無いなら「無い」と明記する）
- 環境メモが前回から更新されている
