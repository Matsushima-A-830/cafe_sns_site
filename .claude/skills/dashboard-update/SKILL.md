# /dashboard-update — Obsidianダッシュボードの更新

`個人開発/cafe_sns_site/cafe_sns_site_dashboard.md`（Obsidian vault内、リポジトリの外）は「いま何が動き、
直近で何をやったか」を人間がスマホ等からでも軽く追える最新状態のスナップショット。
`個人開発/cafe_sns_site/実装履歴/` フォルダはその裏側で、セッションごとに**追記していく**蓄積データ。

**2つは役割が違う。** ダッシュボードは毎回上書き（最新のみ）、実装履歴フォルダは上書きしない（過去のエントリは触らない）。
このスキルは両方を1セットで更新する。

## いつ実行するか

- PR がマージされた（`/board-update` の直後、`/handoff` の前）
- セッション中に人間の判断を仰いだ質問・その場の決定があった
- エージェント成熟度（[[cafe_sns_site_エージェント成熟度]]）のレベル・スコアが変わった
- セッションを区切る直前（引き継ぎテキストを作る前に、その日の作業を先に記録する）

**逆に不要なとき:** コードのリファクタのみ、ドキュメントの誤字修正のみなど、翌日の自分が読んでも得るものが無い変更。

## 前提: Obsidianツールの読み込み

`mcp__obsidian__*` はデフォルトで遅延ロードされる。セッション開始後最初に使うときは
`ToolSearch` で `select:mcp__obsidian__vault_read,mcp__obsidian__vault_write,mcp__obsidian__vault_list` を
まとめて読み込む（1回で済ませる。1個ずつ読み込まない）。

## 手順

### 1. 前回更新からの差分を洗う

```bash
gh pr list --state merged --limit 10          # 直近マージ済みPR
git log --oneline <前回の実装履歴エントリの日付以降>..HEAD
git diff --stat <同上> -- docs/product/pending-items.md
```

「何を実装したか」より、**「その場で判断したこと」「pending-itemsに新規追加・解消した項目」**を拾うほうが重要。
実装内容そのものはPR説明文とdocs側が正なので、ここで重複して書き写さない。

### 2. 実装履歴フォルダに新規エントリを追加する

`個人開発/cafe_sns_site/実装履歴/_テンプレート.md` の構成に従う。

- **ファイル名:** `YYYY-MM-DD_内容の短い要約.md`（同日に複数セッションがあれば `YYYY-MM-DD_2_...`）
- **書く基準:** 「後で読んで文脈が繋がる」最低限の粒度。書きすぎない（この運用自体が「更新のたびに薄まる」ことを避けるために作られた経緯がある）
- **既存エントリは絶対に上書き・編集しない。** 追加のみ

見出し構成（テンプレート通り）:

```markdown
---
date: YYYY-MM-DD
prs: [#番号, ...]
---

# YYYY-MM-DD 要約タイトル

## やったこと
## 判断・決定事項
## 非同期Q&A
## メトリクス（わかる範囲で）
## 次回への申し送り
```

空になる見出し（例: 非同期Q&Aが無かった）は「なし」と一言書くか、見出しごと省略してよい。

### 3. ダッシュボード本体を上書きする

`個人開発/cafe_sns_site/cafe_sns_site_dashboard.md` を最新状態に合わせて**全面的に書き換える**（差分パッチではなく上書き）。

| セクション | 更新内容 |
|---|---|
| `updated`（frontmatter） | 今日の日付 |
| 概況テーブル | エージェント成熟度（[[cafe_sns_site_エージェント成熟度]] frontmatter の `到達レベル`/`ランク`）、マージ済みPR数（`gh pr list --state merged` の最大番号）、オープンなPR数、未決事項🔴の件数、直近セッション日 |
| 直近の実装履歴 | 実装履歴フォルダを新しい順に5件だけリンク。6件目以降はこのセクションから外す（フォルダ自体からは消さない） |
| 未解決の重要事項 | `pending-items.md` の🔴（優先度A未決）を優先し、直近で動きのあった項目を5件程度に絞る |
| 未回答の質問 | セッション中に「今は判断保留」にした質問があれば1行追加。回答が出たら実装履歴エントリ側に詳細を書いてここからは消す |

費用・キャッシュ読み込み率など**このプロジェクトで計測していない指標は書かない**。空欄で埋めない。

### 4. リンク切れを確認する

Obsidianのwikilink `[[...]]` はファイル名（拡張子なし）で解決する。フォルダそのものへのリンク
（`[[個人開発/cafe_sns_site/実装履歴]]`）は解決できない点に注意 — フォルダに触れるときはコードスパン
（`` `個人開発/cafe_sns_site/実装履歴/` ``）で書く。新規作成したファイルへのリンクは、書いた後に
`vault_read` の `unresolvedLinks` を確認して壊れていないか見る。

## やらないこと

- **実装履歴の過去エントリを書き換える** — 追加のみ。過去の記録は「その時点でそう判断した」記録として残す
- **PRの内容をそのまま転記する** — git/GitHub側が正。ここに書くのは「その場の判断」「pending-itemsとの往復」「非同期Q&A」
- **費用・トークン数など未計測の指標を埋める** — 取得できる指標だけ書く
- **このリポジトリへのコミット** — Obsidian vault側の更新であり、`cafe_sns_site` リポジトリの変更ではない。git commit は不要

## サイクルの中での位置

[development-cycle.md](../../../docs/operations/development-cycle.md) の ⑥ 出荷フェーズ、`/board-update` の直後・
`/handoff` の前に置く。

```
⑤ 実機確認・E2E化
      ↓
⑥ 出荷   /board-update → db:reset検証 → PR → CI green → マージ → /dashboard-update   ← ここ
      ↓
⑦ 引き継ぎ   /handoff <次の画面ID> → セッションを切る
```

`/board-update` はリポジトリ内のボード（`docs/implementation-board.html`、設計の正）を更新するのに対し、
`/dashboard-update` はリポジトリ外（Obsidian vault）の運用ログを更新する。**両方必要で、どちらかで代替できない。**

## 他スキルとの関係

- **実装状況ボードの更新:** `/board-update`（このスキルの直前に実行）
- **引き継ぎテキストの生成:** `/handoff`（このスキルの直後に実行。両者は別物 — `/handoff` はターミナル出力のみでファイルに残さないが、`/dashboard-update` はObsidian側に恒久的に残す）
