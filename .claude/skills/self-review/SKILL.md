# /self-review — コードレビュー

## 起動時に必ずやること

1. **変更ファイルの一覧化:** `git status` / `git diff --stat` で範囲確認
2. **変更の意図確認:** タスク・issue・ドキュメントとの整合性
3. **カテゴリごとに走査:** 全ファイルを1回で全観点は無理。以下のカテゴリを順に見る

## レビューの原則

- **Nitpick より Blocker を優先** — 指摘は「重大 / 中 / 軽微」でラベル付け
- **代案を提示** — 「なぜダメか」だけでなく「どう直すか」まで
- **主観と客観を分ける** — 「私の好み」と「規約違反」を混同しない
- **ドキュメント側の不整合を疑う** — コードが正しく docs が古い場合もある

## カテゴリ別チェックリスト

### 1. TDD遵守（コアロジック）

- [ ] 変更されたロジックに対応するテストが存在するか
- [ ] テストが**先に**書かれた形跡（Red → Green）が読み取れるか
- [ ] Happy Path 以外の主要な分岐がテストされているか
- [ ] モックが過剰でないか（内部関数までモックしていないか）
- [ ] RLS を含む挙動は統合テストで検証されているか

### 2. 型安全性

- [ ] `any` が使われていないか（`unknown` + ナローイングを使う）
- [ ] `as` キャストが不必要に使われていないか
- [ ] 外部境界（Server Actions入力・API応答）で Zod 検証しているか
- [ ] `types/database.ts`（Supabase自動生成）を再生成したか

### 3. 認可・セキュリティ

- [ ] RLS に認可を委譲しているか（アプリ層でチェックしていないか）
- [ ] Service Role Client がクライアント側に露出していないか
- [ ] 環境変数を直接 `process.env` で参照していないか（`lib/env.ts` 経由か）
- [ ] Zodスキーマで入力を検証しているか
- [ ] 画像アップロード時に EXIF 除去が実装されているか
- [ ] `.env*` がコミットされていないか

### 4. RLS ポリシー（DB変更時）

- [ ] `alter table ... enable row level security` を書いたか
- [ ] SELECT / INSERT / UPDATE / DELETE それぞれのポリシーを定義したか
- [ ] ブロック関係が適用されているか（該当テーブル）
- [ ] pending_consent ユーザーの操作制限を反映しているか

### 5. 拡張性・変更容易性

- [ ] 責務が単一か（1関数1目的）
- [ ] 依存性が注入可能か（テストしやすいか）
- [ ] enum・マジック文字列が `constants/` に集約されているか
- [ ] Supabase固有APIが薄いラッパー越しに使われているか（将来のAWS移行への配慮）
- [ ] 不必要な抽象化を作っていないか（3回未満のパターンで抽象化していないか）

### 6. バグリスク

- [ ] 早期リターンで浅いネストを保っているか
- [ ] `redirect()` を try/catch で握っていないか（Server Actions）
- [ ] 例外を握りつぶしていないか（catch した後に無視 or console.log だけ）
- [ ] 楽観更新の失敗時ロールバックが実装されているか
- [ ] 空配列・null・undefined の境界がテストされているか
- [ ] 時刻依存ロジックが `Date.now()` を直接使っていないか（テスト時 fake timer）

### 7. UX（フロントエンド変更時）

- [ ] モバイル・タブレット・PC の3レイアウトで崩れないか
- [ ] `loading.tsx` `error.tsx` を用意しているか
- [ ] 空状態のUIとCTAがあるか
- [ ] 破壊的操作に確認ダイアログがあるか（削除・退会等）
- [ ] 下書き自動保存が発火しているか（ブログ投稿）
- [ ] 楽観更新でモバイルの体感速度が確保されているか
- [ ] キーボード操作でフォームが完結するか
- [ ] `alt` テキスト・aria-label が適切か

### 7-b. デザインシステム遵守（[docs/design/design-system.md](../../../docs/design/design-system.md)）

**必ず Grep で機械的に検出する:**

```
禁止パターン (すべて 0 件であること):
  - text-black
  - bg-black
  - border-black
  - #000000
  - #000\b
  - black/[0-9]
  - style=\{
```

**目視チェック:**

- [ ] 余白ユーティリティが `p-0/1/2/3/4/6/8/10/12/14/16/20/24` および `m-*` `gap-*` `space-*` すべてで8倍数（4/12例外）に収まっているか
- [ ] `p-5` `p-7` `p-9` `p-11` `p-13` `p-15` 等の非8倍数余白ユーティリティが使われていないか
- [ ] 任意値 `p-[XXpx]` `text-[XXpx]` `w-[XXpx]` が使われていないか（使う場合は8倍数のみ）
- [ ] テキストサイズが Tailwind 標準の `text-xs/sm/base/lg/xl/2xl/3xl/4xl` のみか
- [ ] カラークラスが `brown-*` `cream-*` `success/warning/danger/info` のみで構成されているか
- [ ] インライン `style={}` が使われていないか（CSS Modules / styled-components も禁止）
- [ ] shadcn/ui 導入時、CSS変数を brown/cream 系に置換したか

### 8. パフォーマンス

- [ ] N+1クエリになっていないか（loop内で個別クエリ発行していないか）
- [ ] SSR/ISR/CSR の使い分けが妥当か
- [ ] 画像は `next/image` を使って最適化されているか
- [ ] 巨大なClient Componentになっていないか（island化）
- [ ] `useEffect` の無限ループがないか
- [ ] インデックスが必要な列に張られているか

### 9. ドキュメント整合性

- [ ] 画面ID コメントが `page.tsx` 冒頭にあるか
- [ ] DB変更が [docs/architecture/data-model/tables.md](../../../docs/architecture/data-model/tables.md) に反映されているか
- [ ] URL変更が [docs/architecture/routing.md](../../../docs/architecture/routing.md) に反映されているか
- [ ] 決定事項が [docs/product/mvp-scope.md](../../../docs/product/mvp-scope.md) と矛盾していないか
- [ ] 新規未決事項が [docs/product/pending-items.md](../../../docs/product/pending-items.md) に追加されているか

### 10. ロジックの見た目

- [ ] 命名が意図を伝えるか（`data`, `temp`, `foo` を避ける）
- [ ] 重複コードが3回目に達したら抽象化されているか（それ以前は放置OK）
- [ ] インラインで書ける関数を切り出しすぎていないか（過剰分割）

### 11. コメント規約（CLAUDE.md 「コメント規約」参照）

- [ ] 各コメントが 1〜2行に収まっているか（3行以上は箇条書き化を検討）
- [ ] 「何を」ではなく「なぜ」を書いているか
- [ ] 型・関数名・変数名で自明な内容を再説明していないか
- [ ] 冗長な言い回し・重複した説明がないか
- [ ] TODO/FIXME に理由と参照先（pending-items のID等）が書いてあるか
- [ ] コミットで一時的に残したデバッグ用コメント（`// console.log(...)` 等）がないか

**Grep で機械検出できる問題:**

```
console.log       残置デバッグ
// TODO(?!:.*\()  理由なしTODO
/\*\s*$          ブロックコメントの空行始まり（多行コメント疑い）
```

## Result 型のフォーマット

レビュー結果はこの形式で:

```
## レビュー: <PR title / task 名>

### 🔴 重大 (Blocker) — マージ前に必ず対応
- [ファイル:行] 内容
  代案: ...

### 🟡 中程度 (Recommended) — 別PRでも可
- ...

### 🟢 軽微 (Nitpick) — 好みの範囲
- ...

### ✅ 良かった点
- ...
```

## 実施しないこと

- **スタイル論争** — Biome/Prettier に任せる
- **好みだけの命名変更提案** — 規約違反でなければ指摘しない
- **全ファイル読破の網羅性** — 影響範囲に集中
- **未変更部分への言及** — 別タスクへ切り出し提案する

## 使い分け（他スキルとの関係）

- **実装中の判断:** `/fe-implement` `/be-implement` `/db-implement`
- **実装後のセルフレビュー:** `/self-review`（このスキル）
- **実装状況ボードの更新:** `/board-update`（レビュー後・PR前）
- **リリース前の総合レビュー:** `/ultrareview`（Claude Code組み込み）

## セルフレビュー vs 他者レビュー

- **セルフ:** 実装直後、Biome/typecheck/testが通ってから走る
- **他者:** PR作成時、GitHubのPR画面で見つけたことをコメント化

## 終了条件

- 重大な指摘がすべて修正 or 明示的に許容された
- テストが Green（`pnpm test:run` `pnpm typecheck` `pnpm lint`）
- ドキュメント側の整合性が確認された
- `/board-update` で実装状況ボードを更新した（実装の意味が変わる変更のとき）
