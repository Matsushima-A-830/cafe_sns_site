# 開発サイクル

Claude Code のスキルを使って1機能を実装し、次のセッションへ渡すまでの一周。

**1周 = 1画面 = 1PR = 1セッション** を単位にする。PR #29〜#46 の実績から逆算して固定した形で、
各フェーズの中身はスキル側（`.claude/skills/<name>/SKILL.md`）に書いてある。このドキュメントは
**フェーズの順序と、その順序である理由**だけを扱う。

- ブランチ・コミット・PR の規約 → [git-workflow.md](./git-workflow.md)
- 環境・CI/CD → [deployment.md](./deployment.md)
- 実装時の作法 → 各スキル

## 全体像

```
① 着手判断        /handoff（引数なし）で候補出し → ユーザーが選ぶ
      ↓
② ドキュメント先行  設計とのズレを実装前に直す / 要判断を潰す
      ↓
③ 実装            /db-implement →(/test)→ /be-implement → /fe-implement
      ↓
④ レビュー2種      /self-review（規約）→ /code-review（バグ）
      ↓
⑤ 実機確認        Playwright MCP で触る → 1〜2本を E2E spec に落とす
      ↓
⑥ 出荷            /board-update → db:reset 検証 → PR → CI green → マージ
      ↓
⑦ 引き継ぎ        /handoff <次の画面ID> → セッションを切る
```

---

## ① 着手判断

引数なしの `/handoff` で候補を3〜4個出し、**ユーザーが選ぶ**。

実績上もっとも強く効いた判断軸は **「404 リンクを塞ぐか」**。

| 着手した画面 | 直前に起きていたこと |
|---|---|
| S_USER_PROFILE_PUBLIC（#34） | #33 が `post-author.tsx` の作者リンクをフィード全カードに乗せ、全部 404 になった |
| S_CAFE_DETAIL（#37） | `post-card.tsx` のカフェ名リンクが全カードから 404 へ向いていた |
| S_MYPAGE（#39） | `middleware.ts` がログイン済みユーザーの `/login` アクセスを `/me` に飛ばすのに、その `/me` が無かった |

**直前の実装が次の 404 を作る**ので、それを塞ぐ形で進めると導線が途切れない。

## ② ドキュメント先行

CLAUDE.md の「設計と実装がズレたら、まずドキュメントを更新してから実装を進める」をフェーズとして置く。

実装前に済ませること:

1. **マイグレーション原文を読む** — `tables.md` は要点のみ。タイムゾーン基準や戻り値の NULL 可能性は
   `comment on function` にしか書かれていない
2. **`routing.md` のレンダリング指定を直す** — ISR 指定は4回連続で実装不能だった
   （閲覧者のセッションが要るページは ISR にできない。[pending-items](../product/pending-items.md) D23 に4件の経緯）
3. **ワイヤーの要素を「出せる / 出せない」に仕分ける** — 出せないものは理由と pending-items 番号をつけて記録する
4. **要判断を `AskUserQuestion` で潰す** — 「停止アカウントのプロフィールを 404 にするか」のような、
   後から変えると影響範囲が広い判断

## ③ 実装

`/db-implement` → `/test` → `/be-implement` → `/fe-implement`。コアロジック（Server Actions・
バリデーション・DB）はテスト先行。

このフェーズで繰り返し出てきた判断が2つある。

- **既存の取得関数を拡張する（自前で書き直さない）** — `getPostList` には `authorId`・`cafeId` を
  足して使い回した。既存関数が黙って解決していること（論理削除の除外・セッション付きクライアントの強制）は、
  新しく書いたクエリでは再現されない
- **RLS で表現できない認可は、アプリ層でなくポリシーを直す** — `follows_insert_own` にブロック判定が
  無かったときは Server Action に `if` を足さず、マイグレーションでポリシーを直した

## ④ レビュー2種

**`/self-review`（規約・ドキュメント整合）→ `/code-review`（バグ探索）の順で両方走らせる。**
守備範囲が違うので片方では済まない。詳細は [self-review スキル](../../.claude/skills/self-review/SKILL.md)。

**レビューを1回で終わらせないこと**が効いている。PR #34 では `/code-review` が4件（うち1件は
404 ページのタイトルに非公開情報が載る漏洩）を出し、その後の人手レビューでさらに6件出た。

## ⑤ 実機確認と E2E 化

Playwright MCP で実際に触る。**確認する観点は、テストで代替できないもの**に絞る。

- 楽観更新のロールバック / リロード後の永続化
- 押下状態（`aria-pressed`）と live region の文言
- 390px 幅での破綻

そのうえで、**「壊れたら気づきたいもの」を1〜2本 E2E spec に落とす**。手の確認はセッションが
終われば消えるので、残さない限り次に壊れたとき CI は気づかない。

この仕組みが無かった時期の画面（#29〜#34）は実機確認も E2E も無いまま残っている
（[pending-items](../product/pending-items.md) D34）。

**このフェーズでしか見つからないものがある。** PR #42 では、書き込みの完了を待たずに
`page.reload()` していたために **WebKit だけで落ちる**不具合が CI で出た。Chromium は間に合って
しまうため、ローカルでは絶対に再現しない。

## ⑥ 出荷

1. **`/board-update`** — [implementation-board.html](../implementation-board.html) を更新。
   実装コミットとは分ける
2. **マイグレーションを含むなら `pnpm db:reset` を実際に流す** — PR テンプレートのチェック項目。
   初期状態から通ることを確認してからチェックを入れる
3. **PR 作成** — 本文は `.github/pull_request_template.md` に沿う
4. **CI が全部 green になるまで待つ** — Playwright は4ブラウザ（chromium / webkit /
   mobile-chrome / mobile-safari）走る。**webkit 系はローカルで動かないので、ここが唯一の検証機会**
5. **Squash Merge**

## ⑦ 引き継ぎ

マージ後に `/handoff <次の画面ID>` を走らせ、**セッションを切る**。

コンテキストが膨らんだ状態で次の機能に入るより、引き継ぎテキストを挟んで切るほうが精度が出る。
引き継ぎテキストは「圧縮したコンテキスト」ではなく **「次が踏む罠のリスト」** なので、
会話の流れを引き継がなくても成立する。

走らせる前に満たすこと:

- PR がマージ済み（レビューで変わった部分が古い前提のまま伝わらないように）
- `/board-update` 実行済み
- 未決事項が [pending-items.md](../product/pending-items.md) に記録済み

## スキル一覧と担当フェーズ

実体は `.claude/skills/<name>/SKILL.md`（フラットな `.md` は認識されない）。

| スキル | フェーズ | 担当 |
|---|---|---|
| `/handoff` | ①⑦ | 着手候補の提示 / 引き継ぎテキストの生成 |
| `/db-implement` | ③ | マイグレーション・RLS・Postgres 関数 |
| `/test` | ③⑤ | TDD の進め方・テストの層の使い分け・E2E の書き方 |
| `/be-implement` | ③ | Server Actions・Route Handlers・Supabase クライアント層 |
| `/fe-implement` | ③ | ページ・コンポーネント・デザインシステム遵守 |
| `/self-review` | ④ | 規約・ドキュメント整合のチェック |
| `/board-update` | ⑥ | 実装状況ボードの更新 |
| `/debug` | 随時 | RLS・キャッシュ・型・環境の詰まり所 |
| （`supabase`） | 随時 | Supabase 一般知識。内容に応じて自動発動 |

**組み込みスキルとの併用:** `/code-review`（④。`ultra` でクラウド多エージェント）・
`/security-review`・`/run` も使う。

> `docs/` 内の過去ログにある `/code-review` は、2026-09-16 の改名前の本プロジェクトスキル
> （現 `/self-review`）を指す。

## スキルを更新するタイミング

**スキルは実装が進むと嘘になる。** 実際、実装着手前に書かれた `/test` と `/be-implement` は、
存在しない API（`getServerSupabase()` / `setupTestDb()` など）を半年近く教え続けていた。

次のときは、その場でスキルを直す（実装 PR とは分ける）。

- スキルのコード例が実物と食い違っているのを見つけたとき
- 同じ罠を2回踏んだとき → `/debug` か該当スキルの「落とし穴」に追記する
- pending-items の記述が誤りだと判明したとき → 実測値つきで訂正する
  （D8 は「lint 失敗する」と書いていたが、実際は `info` が出るだけで終了コードは 0 だった）

## 並列でセッションを走らせる場合

作業ツリーは1つしかないので、**別セッションがブランチを切り替えると相手のファイルが書き換わる**。
実際に、別セッションが作業中のブランチに居合わせたことがある。

- ブランチを切り替える前に `git status` と **その PR がマージ済みか**を確認する
- WSL 実行用の一時スクリプトは固定パス（`/tmp/run.sh`）にしない。セッション固有の名前にする
  （固定パスを奪い合う事故が実際に起きた）
- 本格的に並列化するなら `git worktree add ../cafe_sns_site-<機能名> -b feature/<機能名> origin/main`
  で1ディレクトリ1ブランチにする（未決）
